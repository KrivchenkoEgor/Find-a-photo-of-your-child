# Find Child Photos — интерфейс на PySide6: спецификация

> Имена файлов семейного архива в этом документе заменены на `снимок-NN`, а название архива — на нейтральное: сам архив в репозиторий не попадает, но по одним только именам файлов вместе с логином автора можно восстановить, чьи это фото.

Дата: 2026-09-28
Статус: одобрено пользователем по частям 1 и 2
Источник чисел: `docs/bench-2026-09-28-detektory.md`, `output/bench_20260928_1035.csv`

## 1. Что это и для кого

Десктоп-приложение (macOS + Windows) для родителя, который ищет фотографии своего ребёнка в
семейном архиве. Повторяет функционал консольного `Findchild.py` в графическом интерфейсе,
но с двумя изменениями принципиального свойства:

1. **Порог сходства — настройка в интерфейсе**, а не число в коде. Он подбирается под архив,
   и один запуск не последний.
2. **Найденные фото сначала показываются, потом копируются.** Молчаливое копирование,
   как в эталоне, недопустимо: оценки «своих» фото лежат в полосе 39…67%, и отличить
   удачу от промаха может только человек.

Пользователь — не программист. Отсюда требование к словам в интерфейсе (раздел 6).

## 2. Что показали замеры на реальных данных

Архив: 131 фото 24 Мп. Эталоны: 16 файлов, 22 лица (в `ref/` несколько разных людей).
20 файлов пользователь подтвердил глазами как «ребёнок на фото есть».

| Факт | Число | Что из этого следует |
|---|---|---|
| Время на фото при 2400 px | ~1.4 с замером (чтение 255 + YuNet 348 + InsightFace 771 мс); боевым прогоном через приложение — 1.56–1.93 с на снимок, см. раздел 8 | один фоновый поток, не пул процессов |
| Уменьшение до 1200 px (наследие эталона) | отнимает 3–7 п.п. сходства | по умолчанию 2400 px |
| Больше 2400 px | прироста нет | выше не предлагать |
| Максимум сходства по архиву | 67.4% | обещать «90% совпадение» нельзя |
| Худшее подтверждённое фото | 39.2% | порог по умолчанию 0.38 |
| YuNet один на 20 подтверждённых | 19/20 при любом пороге | «Быстрее» не может дать полный ответ |
| InsightFace один на 20 подтверждённых | 20/20 при 0.38 | «Точнее» = базовый вариант |
| Оба детектора (max) при 0.38 | 20/20 и 0 лишних | рекомендуемый режим |
| Корреляция оценок двух детекторов | 0.984 | разница — в скорости и полноте |
| genderage на детских лицах | «мужчина 29–36 лет» на подтверждённых фото девочки | фильтров по полу/возрасту нет |

## 3. Конструкция: почему один поток + кэш

Рассмотрены три варианта. Взят **A — один фоновый поток + кэш отпечатков**.

- **B (пул из 6 процессов, как в `Findchild.py`)** в 4–5 раз быстрее на большом архиве, но:
  3–4 ГБ RAM, старт ~20 с, сложнее отмена, и `multiprocessing` внутри PyInstaller-приложения
  на macOS перезапускает исполняемый файл (`freeze_support()`) — типичная поломка при упаковке.
- **C (два прохода: быстрый отсев → точная проверка)** экономит только на папках без лиц.
  В этом архиве лица есть на 131 из 131 фото, то есть выигрыша нет, а место, где фото
  может потеряться, появляется.

Кэш делает однопоточность терпимой: тяжёлый проход по папке случается один раз,
дальше смена порога и повторный запуск мгновенные.

## 4. Модули

```
src/
├── main.py            # QApplication, создание главного окна
├── core/
│   ├── engine.py      # загрузка моделей; единый интерфейс FaceEngine
│   ├── yunet.py       # FaceEngine: YuNet + распознавание по его точкам
│   ├── insight.py     # FaceEngine: InsightFace (RetinaFace + arcface)
│   ├── both.py        # FaceEngine: оба детектора, лица объединяются (см. ниже)
│   ├── scanner.py     # обход папок, фильтры форматов и служебных каталогов
│   ├── cache.py       # SQLite-оглавление отпечатков, ключи инвалидации
│   ├── matcher.py     # образ → проценты по каждому фото
│   ├── etalon.py      # вся арифметика окна эталона, без Qt: кто anchor и что пойдёт в поиск
│   ├── worker.py      # QThread: прогресс, отмена, сигналы в UI
│   ├── copier.py      # копирование отмеченных, уникальные имена
│   └── report.py      # report.txt + CSV
├── ui/
│   ├── main_window.py # три шага в одном окне
│   ├── reference_dialog.py  # модальное окно: несколько снимков, сетка лиц, ОК
│   ├── face_picker.py # как нарисовать лицо карточкой (кроп, номер, QPixmap)
│   ├── results_view.py# сетка миниатюр, галочки, две кучки
│   └── settings.py    # ползунок похожести, режим детектора, качество разбора
└── utils/config.py    # QSettings: сохранить настройки между запусками
```

**Границы, которые важно держать:**

- `FaceEngine` — единственный интерфейс к моделям: `detect(image) -> list[Face]`,
  где `Face = (box, landmarks5, embedding)`. Третий режим (`both.py`) — тоже `FaceEngine`.
  UI про устройства моделей ничего не знает.
- `matcher.py` **не знает про порог**. Он отдаёт число на фото; где отсечь — решает UI.
  Именно поэтому ползунок мгновенный.
- `etalon.py` — единственное место, где решают, **кто такой anchor и что пойдёт в поиск**.
  Без Qt, поэтому проверяется без окна. `reference_dialog.py` только рисует то, что он
  вернул, и пересылает обратно набор отметок. Порог приемства импортируется из
  `matcher.REF_MIN_SIM`, а не переписывается: два владельца одного числа однажды
  расходятся, и окно начинает обещать не то, что делает сравнение.
- `cache.py` не читает фото и не вызывает модели — только SQLite.
- Порядок точек YuNet передаётся в `norm_crop` **как есть, без перестановок** — это
  проверено перебором (`bench_calibrate.py`: 0.898 против 0.403 при перестановке глаз).
- `both.py` определяет поведение режима «Оба»: запускаются оба движка, их лица
  объединяются, совпадающие (пересечение рамок больше половины площади) считаются одним
  лицом и от одного из них берётся то, у которого рамка больше. Все полученные отпечатки
  уходят в `matcher`, а он уже берёт максимум — поэтому «Оба» находит всё, что нашёл бы
  любой из детекторов по отдельности, и ничего не теряет на случае `снимок-01`.

## 5. Кэш отпечатков

Файл: `<папка служебных данных>/FindChild/cache.sqlite3`
(macOS `~/Library/Application Support/`, Windows `%APPDATA%%`). **Не** рядом с фото —
в чужой папке с семейным архивом мусорных файлов оставлять нельзя.

```
photos(
  path TEXT,        -- абсолютный путь к фото
  mtime INTEGER,    -- время изменения файла
  size INTEGER,     -- размер в байтах
  engine TEXT,      -- 'yunet' | 'insight' | 'both'
  max_dim INTEGER,  -- 1200 | 2400
  faces BLOB,       -- JSON: box, landmarks, embedding (float32 base64)
  PRIMARY KEY (path, mtime, size, engine, max_dim)
)
```

Правила:
- Фото изменилось (mtime/size) или сменились `engine`/`max_dim` — записи для этого ключа
  нет, фото сканируется заново. Старые записи не удаляются и не мешают.
- Фото пропало из папки — его просто не находит `scanner`, чистка не обязательна.
  Отдельная команда «очистить кэш» в настройках всё же будет.
- Отмена посреди разбора сохраняет уже сделанное: следующий запуск продолжает с места остановки.
- Кэш содержит только отпечатки и координаты, **сами фото не копируются**.

## 6. Экраны и поведение

Одно окно, три шага сверху вниз. Без wizard-диалогов.

**Шаг 1. Где ищем.** Ровно две кнопки, и обе делают одно: **«Добавить папку с фото»**
дополняет список, **«Убрать все»** его очищает. Замещающей кнопки в окне нет — прежде
«Выбрать папку» стирала принесённое молча, и отличить дополняющее действие от замещающего
по названию нельзя. Под кнопками — список полных путей и счётчик «найдено N фото, папок M».
Кнопка «Начать разбор папки». Полоса процента, счётчик «обработано 47 из 131», кнопка
«Остановить». «Убрать все» не трогает уже снятые лица: разбор стоит минуты.

**Шаг 2. Кого ищем.** Одна кнопка «Выбрать фото ребёнка» открывает **модальное окно**:

- внутри — «Добавить фото…», несколько файлов за раз; можно добавлять несколько партий;
- приложение само ищет лица на добавленных снимках, с прогрессом внутри окна;
- все найденные лица — **одна плоская сетка карточек** с множественной отметкой, а не
  пошаговый опрос по каждому файлу;
- файл с одним лицом -> карточка отмечена автоматически; файл с несколькими -> ни одна
  не отмечена, угадывать нельзя; файл без лиц -> серая карточка «лицо не найдено»;
- на каждой отмеченной карточке — **число**: насколько это лицо похоже на самое крупное
  из отмеченных. У крупнейшего — 100.
  **Anchor — самое крупное годное отмеченное лицо, а не то, по которому кликнули первым:**
  ответ не имеет права зависеть от истории движений мыши;
- отмеченное с числом ниже 40 % гаснет и получает подпись **«в поиск не пойдёт»**. Молча
  выбрасывать отметку прежний код не имел права — человек ставил галочку, и ничего не
  происходило. В поиск она не берётся: одно чужое лицо в эталоне начинает находить
  чужого человека по всему архиву, и отличить его потом нельзя;
- «ОК» переносит выбор в главное окно и пересчитывает проценты на месте, нового разбора
  папки нет. «Отмена» не меняет ничего.

В главном окне под кнопкой — честный счётчик: «ищем по эталону: лиц N, снимков M», и если
часть отметок не пошла в поиск — слово про это рядом.

**Шаг 3. Что показало.** Сетка миниатюр, сортировка по убыванию числа. На каждой миниатюре
рамка найденного лица и процент. Две кучки:
- **«Похоже»** — не ниже настроенного числа, галочки проставлены;
- **«Слабое сходство»** — свёрнута, но с явной подписью «ещё 7 фото, похоже слабее —
  нажмите, чтобы посмотреть». Нужна, чтобы не терялись случаи вроде `снимок-01`
  (28% у быстрого детектора).

**Настройки — над результатами, применяются мгновенно.** Полоса в две строки: в первой
подпись ползунка, ползунок и число, во второй — способ поиска, качество разбора и
«Очистить оглавление». Одной строкой метку похожести обрезало до «Насколько фото должно
бы…», а обрезанная подпись настройки — это настройка, которую человек не прочитал.
- ползунок «Насколько фото должно быть похоже», диапазон 0.30…0.60, по умолчанию **0.38**;
  подсказка рядом: «выше 67% не бывает даже когда ребёнок на фото точно есть»;
  влево = больше фото, вправо = только явные;
- «Быстрее / Точнее / Оба», по умолчанию **«Оба»**; в подписи — минуты на текущем архиве;
- «Качество разбора: обычное (быстро) / внимательное (точнее)», по умолчанию **внимательное**;
  смена качества означает новый разбор папки, и приложение это честно предупреждает.

Подпись под сеткой объясняет число на карточке и обязана брать текущее значение ползунка
из настройки, а не хранить замер в тексте: зашитое «45 %» читалось как обещание при
ползунке на 38.

**Кнопка «Скопировать отмеченные»** → выбор папки → копирование с сохранением имени,
при конфликте суффикс `_1`, `_2` (поведение `copy_with_unique_name` из эталона).
Рядом создаются `report.txt` и CSV.

**Слов нет в интерфейсе:** «порог», «уверенность», «embedding», «косинусное расстояние»,
«детектор», возраст, пол. Объяснение настройки — подпись колонки плюс факт из данных.

## 7. Ошибки

| Случай | Поведение |
|---|---|
| Файл не читается | разбор продолжается, файл в список «не обработано» в отчёте |
| На эталонном фото лиц нет | просить другое фото, результат не показывать |
| В окне эталона: фото не разобралось | отдельная карточка «фото не разобралось», не путать с «лицо не найдено»: неразобранный файл называется неразобранным |
| В окне эталона: сняли флаг со всех отметок | «ОК» выключено и сказано почему, а не возвращён пустой эталон |
| В окне эталона: все отмеченные лица отвергнуты | «ОК» выключено, человек видит числа; молча отдать пустой образ нельзя |
| В окне эталона: закрывают крестиком посреди разбора | поток остановлен и дождался, оглавление не закрывается под живым потоком |
| Модель `buffalo_l` не скачана (290 МБ) | плашка «скачиваем модель распознавания», без вида зависшего окна |
| HEIC не открывается | то же, что и нечитаемый файл; причина в отчёте |
| Пользователь нажал «Остановить» | завершить текущее фото, сохранить в кэш, показать частичный результат |
| Папка без фото | сказать прямо, не показывать пустую сетку как успех |
| Нет прав на запись в папку результатов | объяснить и предложить другую папку |

## 8. Тестирование

**Быстрые тесты (без моделей, доли секунды)** — `tests/`, pytest, подставной `FaceEngine`:
- `cache`: запись/чтение, устаревание при изменении mtime, size, engine, max_dim;
- `matcher`: максимум по лицам и по эталонам, пустое фото, фото без лиц;
- `copier`: уникальные имена, не затирает существующий файл;
- `scanner`: фильтры форматов, рекурсия, служебные папки, сортировка;
- `worker`: отмена, сигналы прогресса, сохранение частичных результатов.

**Боевой тест на реальных данных** (помечен `slow`, запускается по явному требованию):
при 2400 px, режиме «Оба» и числе 0.38 все 20 подтверждённых файлов из
`CONFIRMED` (`analyze_threshold.py`) в кучке «Похоже» и ни одного лишнего.
Если папки `data/` нет — тест пропускается, а не падает: фото ребёнка не в репозитории.

**Прогон 2026-09-29, `tests/test_golden_archive.py` (6 медленных тестов, четыре повтора
полного прогона):** подтверждённых найдено 20 из 20, лишних 0, пропущено 0 — приложение
повторяет замер детекторов один в один. Эталон от главного снимка из `ref/` (морда 307 px):
в образ принято 12 лиц из 24 рассмотренных (раздел 2 говорит о 22 лицах в `ref/` — это
подсчёт одним детектором, режим «Оба» видит 24). Архив: 131 снимок, 1101 лицо до слияния детекторов,
567 после. Время: загрузка моделей 7.7–9.9 с, холодный прогон 205–253 с (1.56–1.93 с
на снимок), повторный прогон по тому же оглавлению — сотые доли секунды и ноль обращений
к моделям. Худшее подтверждённое фото 40%, лучшее 68%: запас до порога 0.38 — 2 п.п.,
поэтому порог и вынесен в ползунок.

**Слияние лиц на этом же прогоне (числа вместо опасений):** правило `merge_faces`
сворачивает рамки на 131 снимке из 131, всего 534 лица. Оно занижает лучшую оценку
на 45 снимках (сильнее всего — `снимок-02.jpg`, 29% → 18%), но из кучки «похоже» не
выбрасывает ни одного подтверждённого фото: единственное сброшенное ниже порога —
неподтверждённый `снимок-03.jpg` (39% → 29%). Лицо, давшее бы лучший ответ без слияния,
схлопнулось в 12 случаях из 20 подтверждённых; заметно ответ оно не сменило — у семи
файлов итоговое число стало на 1–3 п.п. ниже (например, `снимок-04.jpg` 54% → 51%),
у остальных осталось тем же. Правило оставлено как есть;
`test_sliyanie_lic_na_gruppovyh_foto_merno` следит, чтобы слияние не теряет подтверждённых
фото, а `test_razpoznavanie_v_rezhime_oba_odin_obekt` — что модель распознавания в режиме
«Оба» поднимается один раз.

**Регрессия окружения:** `check_env.py` (10 проверок) и `check_models.py` (реальная детекция)
запускаются на новой машине до разработки. Базовые числа: YuNet находит лицо на
`assets/samples/test_face.jpg` за ~11 мс, embedding 512 измерений, норма 1.0000.

## 9. Вне рамок этой версии

- Поиск сразу по нескольким детям (решение пользователя: один ребёнок за запуск).
- Пул процессов и ускорение на многоядерности.
- Фильтры по полу и возрасту.
- Автоматическая группировка архива «по людям» (кластеризация всего архива).
- Импорт из «Фото» macOS и из iPhone напрямую — только папки на диске.
- Подпись и notarization для macOS.

## 10. Сборка (следующий этап, не этот)

PyInstaller: `--onefile --windowed`, модели через `--add-data`, путь через `sys._MEIPASS`.
Windows: `installer_win.iss` (Inno Setup). macOS: `build_dmg.sh` (create-dmg), без подписи —
в README обязательны два способа обхода Gatekeeper. Проверять сборку надо на той же ОС,
для которой она делается: `.exe` с macOS не собирается.

## 11. Приватность

`data/`, `ref/`, фото-расширения и `.env` закрыты в `.gitignore`. Архив с фото ребёнка
не выгружается ни в один внешний сервис, вся обработка локальная. Отчёты содержат
имена файлов и числа, но не изображения.
